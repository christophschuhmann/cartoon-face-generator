Batch the groups,
keep the questions.

527 AudioSet classes, ten seconds of audio history, a 200 ms target, BF16. Original 64-class multi-label groups remain unchanged. Only the number of independent groups processed together changes.

Result

Eight groups per GPU batch reduced median window inference from 2.091 s to 1.676 s: 19.9% less time, or 1.25× throughput. Two groups already capture most of the benefit and require less memory. Four groups did not improve the median over two in this small run.

A separate follow-up put all nine groups into one verified model forward and measured 1.572 s. This still falls well short of processing all 527 classes every 200 ms.

These are isolated experimental paths, not a deployment change. The public demo still uses its previous sequential group loop. Batching does not solve the model’s previously observed time-localization errors.

Repeated-target audio also worked at batch 8: 1.910 s in the single follow-up measurement, maximum score difference 0.005351 from the corresponding sequential run.

What was changed in the experiment?

  1. Send several (state, questions, media) requests together through the documented system_one_batch interface. Keep each original 64-class multi-label question intact; the last group has 15 classes.
  2. Raise the runner’s padded-token budget from the production limit of 4,096 to 65,536 for the bounded experiment. Otherwise a batch API call could still be internally split. Instrument _slot_logits to count the actual forward passes and their row lengths.
  3. Reuse preprocessing for the identical audio/context. Verify the exact repeated mel tensor and mask pattern before reusing projected audio features across batch rows. Clip order is preserved, including the optional repeated target.
  4. Preserve native independent scores. No softmax across AudioSet classes, no missing-class zero fill, no scene/prompt changes, and no cross-window reuse of incompatible features.

A native batch-8 run without feature reuse took 1.759 s, compared with 1.721 s for the deduplicated run. This single pair is too small to claim a reliable standalone speedup. Deduplication encoded one clip instead of nine repeated copies; the maximum score difference from the native batched run was 0.003968. Reduced-precision kernels can depend on batch shape, so feature reuse is not claimed bit-identical to the native multi-clip encoding.

Warm-up, deployment and next steps

Model loading took 23.83 s and is excluded from the warm table. Each batch shape was exercised before timing. The experiment used the exact checkpoint 81222dae8bf8bdd7f903643b5b2a8803bf2e3176, PyTorch 2.6.0+cu124, BF16 and eager execution; torch.compile remained disabled.

Robby, TTS, ASR and the resident decision model on GPU 0 were not stopped or reconfigured. The test model used GPU 1, then exited and released its memory. Production timings and live latency have not been remeasured with this experimental batching path because it has not been installed in the service.

For integration, batch all groups when the token/VRAM budget permits, with smaller batches as a fallback. Batch 2 is an attractive low-memory choice; batch 8 or all 9 give the best measured throughput. First validate long scene descriptions, 20-second history, repeated targets and GPU contention. The current short-context tests do not establish those operating limits.
